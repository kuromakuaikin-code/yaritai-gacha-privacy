# Threads 運用戦略（設計書）

作成日：2026年8月12日 / 対象：盆踊り・地域祭りナビ東海、東海おでかけナビ

この文書は**設計だけ**で、実装コードは含まない。決めた前提は次の3つ。

| 項目 | 決定 |
|---|---|
| プラットフォーム | Threads 単独 |
| 自動化の範囲 | **下書き生成のみ**。投稿は人が手で行う（API 連携なし） |
| 目的 | 自サイト群（盆踊りナビ・おでかけナビ）への流入と、来年分のデータ収集 |

---

## 0. 結論

1. **アカウントは1つに統合する。** 盆踊りナビ単独では年10か月ネタが尽きる。「東海のローカルおでかけ情報」という1つの軸に、盆踊りナビとおでかけナビを両方載せる。
2. **今シーズンは間に合わない。今年は型の検証、勝負は来年7月。** 盆踊りの残り開催はあと11日で、Threads のフォロワーがゼロから育つ時間はない。今年の8月は「投稿の型が回るか」を実地で試す期間と割り切る。
3. **最大の障害は Threads ではなくデータ在庫。** 1月・2月・5月は投稿ネタが**実データで0件**ある。ここを埋めない限り、どんな投稿設計も週2回で止まる。

|---|---|---|
| 1 | アカウント開設、8/13〜8/23 の残り115件で投稿の型を実地テスト | 今週 |
| 2 | `odekake/spots.json` のイルミネーション（現在**1件**）とあじさい（**2件**）を拡充 | 9月まで |
| 3 | `coverage.json` の未確認56市区町村を「情報を探しています」投稿の在庫に変換 | 9月から |

## 1. なぜ Threads か

### 調べて分かったこと（確度別）

egress ポリシーで Meta 公式ドキュメント（`developers.facebook.com`、`about.fb.com`）に直接アクセスできなかったため、検索インデックス経由で複数ソースを突き合わせた。確度を分けて記載する。

| 事実 | 確度 | 運用への意味 |
|---|---|---|
| 1投稿の上限は500文字（2024年の300文字から拡大） | 高（複数ソース一致） | イベント情報を1投稿に収めきれる。X の140文字と違い分割不要 |
| 月間アクティブ5億突破（Meta 発表、2026年6月） | 高 | — |
| 日本の MAU は1,500万〜1,700万、利用時間は前年比130%超 | 中（推定値、ソースにより幅） | 東海4県のローカル情報でも母数は足りる |
| 「おすすめ（For You）」に**地域的な親和性**が働く | 中（複数ソースが指摘、Meta 公式の明言は未確認） | **ローカルイベント情報と構造的に相性がよい。これが Threads を選ぶ最大の根拠** |
| コミュニティ機能が2026年6月に日本導入、日本語トピックタグ新設 | 高 | 地域・お出かけ系コミュニティがあれば主戦場になる。**開設時に実機で要確認** |
| 1投稿に設定できるトピックは1つだけ | 中 | ハッシュタグを並べる X 型の運用は使えない。1つを選ぶ設計が要る |
| 公式の予約投稿機能あり（最大75日先、Web版でも可） | 中〜高 | **「下書き生成のみ」の運用がこれで成立する**（後述の週次バッチ） |
| リプライがいいねより重く、投稿直後の初期反応が効く | 中（複数ソース一致） | 告知の垂れ流しは伸びない。**問いかけ型の投稿を混ぜる必然性がある** |
| インサイトあり（ビュー数、閲覧のソース、フォロワーの地域分布） | 中〜高 | 効果測定が Threads 側だけでもできる |

### Threads に向いていないもの

**こえかえ・婚活デートメモ・何日もった？・やりたいガチャの4アプリは、このアカウントに載せない。**

Threads で伸びるのは「継続的にネタが出るもの」で、アプリは新機能リリース時しかネタがない。地域イベントは毎日ネタが出る。同じアカウントに混ぜると「何のアカウントか」が曖昧になり、For You の地域親和性にも乗らなくなる。アプリの告知は、アカウントが育った後に**年数回の例外**として出す。

## 2. アカウント設計

**推奨：「東海のおでかけ・お祭り情報」1アカウントに統合する。**

| 案 | 内容 | 評価 |
|---|---|---|
| **A（推奨）** | 盆踊りナビ＋おでかけナビを1アカウントに統合 | 年間の投稿を継続できる唯一の形。地域軸が一貫し For You に乗る |
| B | サイトごとに2アカウント | 盆踊り側が年10か月沈黙する。アルゴリズム評価が維持できない |
| C | 個人アカウントで全部（アプリ含む） | 軸が定まらず、地域親和性が効かない |

判断を左右する軸は「継続性」「軸の一貫性」「運用負荷」の3つで、A は3つとも B・C に勝る。B の唯一の利点（サイトごとの純度）は、統合しても投稿文で区別できるため実質的な損失にならない。

プロフィールに書くこと：対象地域（東海4県）、扱う情報（盆踊り・地域祭り・桜・あじさい・紅葉・イルミ）、**情報元を確認して載せている**という運用姿勢。最後の1点が、まとめサイトとの差別化になる。

## 4. 在庫ギャップの埋め方

推奨順に4つ。1と2で空白期の大半が埋まる。

### ① 未確認地域を「情報を探しています」投稿に変換する ★最重要

`coverage.json` に未確認の市区町村が**56件**（`unknown`）、公式発表待ちが10件（`waiting`）、確認中が3件（`review`）入っている。これを1件1投稿の在庫として使う。

```
【情報を探しています】名古屋市千種区の盆踊り

千種区の学区・町内会の盆踊り、まだ1件も確認できていません。
区役所のサイトにも今年の一覧が見当たらず、回覧板や掲示板だけで
告知されているものが多いのだと思います。

千種区にお住まいの方、「うちの学区でやってる」という情報が
あれば教えてください。日付が分からなくても、
「〇〇公園でやってた気がする」だけで十分助かります。
```

これが効く理由は3つ重なっている。

1. **リプライを誘発する。** Threads はリプライを重く見るので、告知型より構造的に伸びやすい。
2. **来年のデータが実際に集まる。** ADMIN.md の「情報収集のコツ」を SNS に開いた形になる。回覧板レベルの情報は検索では出てこないので、住民に直接聞くのが唯一の経路。
3. **季節を問わない。** 56件あるので、9月〜翌6月の空白10か月を週1ペースで埋めきれる（約13か月分）。

**空白期のネタ切れと、来年の情報収集という2つの課題が、同じ行動で解ける。** これが今回の設計で一番価値のある部分だと考える。

### ② 1イベントを複数回使う

1イベント1投稿という前提を捨てる。1件を最大5回使える。

| タイミング | 投稿の型 |
|---|---|
| 掲載時 | 「今年も開催が確認できました」 |
| 1週間前 | 「来週末はここ」 |
| 前日・当日朝 | 「今夜」 |
| 中止・延期の発生時 | **速報**（後述、最も価値が高い） |
| 終了後 | 「来年もこの時期」（翌年の予告として） |

在庫221件が実質1,000投稿相当になる。ただし7〜8月の偏りは解けない（同じ月に5回使うだけ）ので、①との併用が前提。

### ③ おでかけナビのデータを増やす（SNS 運用の前提条件）

イルミネーション1件・あじさい2件では、1〜2月・5月・6月が回らない。**イルミを最低15件**入れれば、11月〜翌2月が紅葉→イルミで連続する。

イルミは盆踊りと違って**会場が毎年ほぼ同じで、点灯期間も安定している**（README の指摘どおり）ため、一度入れれば毎年使い回せる。投資対効果が最も高いデータ拡充先。

> ⚠️ 現在の `spots.json` は `source` が Walkerplus 等のまとめサイトで、`verifyStatus: "要確認"` のまま。ADMIN.md の「競合サイトからは転載しない、入口としてだけ使う」に照らすと、**SNS に出す前に一次情報での確認が必須**。拡散すると誤情報の影響がサイト掲載時より大きくなる。

### ④ 束ねる投稿

「今週末の東海、盆踊り27件」のように、複数件を1投稿にまとめる。8月のように在庫過剰な時期に、投稿数を増やさずに情報量を出す手段。個別イベントの深掘りと交互に出す。

## 6. 投稿の型

500文字上限。トピックは1投稿1つ。事実部分（【】内と ▶ 行）は**データから機械的に埋める箇所**で、AI が書き換えてはいけない。

### 型A：当日告知（盆踊り・祭り）

```
【今夜】名古屋市中川区・万場盆おどり大会

▶ 8月12日(水) 18:00〜21:00
▶ 会場：万場川東公園（名古屋市中川区万場）
▶ 小雨決行。中止の場合は当日の町内掲示板に掲示

踊りは19時から。模擬店が出ます。
会場周辺は車両通行止めになるので、自転車は指定の駐輪場へ。

情報元：名古屋市中川区公式サイト（8月10日確認）
```

`rain` `venue` `dates` `desc` `source` `lastVerified` をそのまま流し込む。**「情報元と確認日を毎回書く」のが、まとめサイトとの差別化点**であり、Threads 上での信頼の作り方でもある。

### 型B：中止・延期速報 ★最も価値が高い

```
【中止】8月15日の〇〇盆踊り大会が中止になりました

台風接近のため、主催者が本日15時に中止を発表。
順延はなく、今年は開催されません。

同じ8月15日の東海4県では、屋内開催の△△（□□市）が
予定どおり実施予定です。

情報元：〇〇町内会公式サイト（8月14日確認）
```

中止情報は検索では出てこず、SNS でしか流通しない。ADMIN.md も「中止情報こそ利用者に価値がある」としている。**保存・共有されやすく、フォローの動機になる投稿はこれ。** `eventStatus` が `cancelled`/`postponed` に変わった時に即時作る。

### 型C：情報募集（空白期の主力）

前掲の①のとおり。`coverage.json` の1件を1投稿に。

### 型D：週末まとめ（金曜）

```
【今週末の東海】盆踊り・地域祭り 49件

8月15日(土) 27件 / 8月16日(日) 9件
愛知19・岐阜11・三重4・静岡2

規模の大きいもの：
・〇〇まつり（△△市）花火あり
・□□盆踊り大会（◇◇市）3日間

町内会・学区レベルの小さいものも載せています。
全部の日程と会場は、リプライのリンクから。
```

### 型E：運営の裏側（リプライを誘いやすい）

```
盆踊りの情報を集めていて一番困るのは、
「去年やってたのに今年の告知がどこにもない」というケースです。

回覧板と掲示板だけで告知される盆踊りは、
ネット上に情報が一切残りません。

いま東海4県で197件を載せていますが、
実際にはこの3倍はあると思っています。

みなさんの町内会の盆踊り、ネットに情報出ていますか？
```

問いかけで終える。Threads のリプライ重視のアルゴリズムに最も適合する型。

### 型ごとの配分（シーズン中の1週間）

| 型 | 本数 | 狙い |
|---|---|---|
| A 当日告知 | 5 | 実用価値、リピート視聴 |
| B 中止速報 | 発生時 | 拡散、フォロー動機 |
| D 週末まとめ | 1 | 網羅性の提示、サイト流入 |
| E 裏側・問いかけ | 2 | リプライ獲得、アルゴリズム評価 |

告知だけを並べると伸びない。**E を必ず混ぜる。**

## 7. AI の役割分担

投稿の誤りは、サイトの誤りより実害が大きい。訂正が届かず、拡散した情報だけが残るため。コミット `672f36a`「公開中の誤情報を修正し、実害につながる経路を塞ぐ」の方針を、SNS 側にも構造として持ち込む。

**原則：AI に事実を書かせない。間違えても実害が出ない部分だけを担当させる。**

| AI がやること | AI がやらないこと |
|---|---|
| 今日どの3件を出すか選ぶ | 日付・時刻・会場・住所を書く |
| 導入文・フックの言い回しを作る | 中止／延期かどうかを判断する |
| 1週間の型の配分を組む | 「例年どおり」等の推測を書く |
| 型E（裏側・問いかけ）の素案を書く | データにないイベントに言及する |
| リプライ返信の下書きを作る | `desc` を書き換える |

事実部分は `events.json` / `spots.json` から**テンプレートの穴埋めで機械的に生成**する。AI が触れるのは穴埋めの外側だけ。これにより、AI が日付を1日ずらす経路が構造的に存在しなくなる。

### 投稿に出す前のゲート

下書き生成の段階で、次に当たるものは自動的に除外する。

| 条件 | 理由 |
|---|---|
| `status` が `published` でない | `pending`（未確認）を確定情報として流さない |
| `posterType` が `resident` | 住民からの未確認情報は SNS で拡散しない |
| `lastVerified` が90日以上前 | 情報が古い可能性がある |
| `verifyStatus` が `"要確認"`（おでかけナビ） | 一次情報未確認。**現在24件すべてが該当**するため、拡充時に解消が必要 |
| `sample: true` | 仮データ |

## 8. 運用フロー（下書き生成のみ）

「下書き生成のみ」を**毎日コピペする運用**にすると続かない。Threads の公式予約投稿（最大75日先）を使い、**週1回のバッチ**にする。

### 平常時（週1回・所要30分程度）

1. **日曜夜**：翌週7日分の下書きを生成 → `sns/drafts/2026-W34.md`
2. **目視確認**：事実部分はテンプレ済みなので、見るのは「選定が妥当か」「型の配分」「文章が不自然でないか」の3点だけ
3. **一括予約**：Threads の投稿画面 →「もっと見る」→ 日時指定で7本を予約
4. **平日は放置**：リプライへの返信だけ行う（アルゴリズム上ここが効くので、返信は手を抜かない）

### 例外：中止・延期速報

即時性が命なので予約に乗らない。`events.json` の `eventStatus` を更新するタイミングで投稿文も作り、その場で手動投稿する。**シーズン中はこれだけ別扱いにする。**

### 週次下書きファイルの形

```markdown
## 2026-08-17 (月) 18:30  [型A 当日告知]
トピック: 盆踊り
リンク: （1つ目のリプライに）https://...bon-odori/e/xxx.html

【今夜】...本文...

---
確認: status=published / posterType=admin / lastVerified=2026-07-10
```

投稿日時・型・トピック・リンク位置・本文・確認情報を1ブロックにまとめる。人はブロックごとにコピペするだけで済む。

## 9. リンクをどこに置くか

**結論が出せなかった。実測で決める。**

調査したソースが割れている。

| 説 | 主張 |
|---|---|
| 本文リンクは不利 | リンク付き投稿はエンゲージメントが30〜50%低下。本文はテキストのみにして、リンクは1つ目のリプライに置く |
| ペナルティは軽い | X ほどの抑制はなく、本文リンクでも For You に乗る |

どちらも一次情報での裏付けが取れていない。推測で決めず、**Cloudflare Web Analytics が既に入っていることを使って自分で測る**。

### A/B の手順（2〜3週間）

1. 週の前半（月〜水）：本文にリンクを入れる
2. 週の後半（木〜日）：本文はテキストのみ、1つ目のリプライにリンク
3. 毎週、次の2つを突き合わせる
   - Threads インサイトの**ビュー数**（＝リーチが落ちるか）
   - Cloudflare Web Analytics の **threads.net / threads.com からのリファラ数**（＝実際に何人来たか）
4. 「ビュー×クリック率」の積が大きい方を採用

リーチだけ見て判断しない。**リプライに置いた方がリーチは伸びてもクリックは減る**可能性があるため、最終的に見るのはサイト流入数。

暫定の初期設定は「リプライに置く」。不利という説の方が具体的な数値を出しているため、まずそちらから始めて反証を取る。

## 10. 測定と判断基準

| 指標 | 取得元 | 見る理由 |
|---|---|---|
| ビュー数 / 投稿 | Threads インサイト | 型ごとの当たり外れ |
| リプライ数 | Threads インサイト | アルゴリズム評価の主因 |
| フォロワーの**地域分布** | Threads インサイト | 東海に寄っていなければ届け先を外している |
| 閲覧のソース | Threads インサイト | For You 経由か、フォロワー経由か |
| threads からのリファラ | Cloudflare Web Analytics | 唯一の「実際の成果」 |
| 情報提供リプライの件数 | 手集計 | ①の投稿が機能しているか |

### 継続・撤退の判断

判断は**来年2月末**に行う。半年で結論を出す。

| 状態 | 判断 |
|---|---|
| フォロワーの地域分布が東海に寄っている | 継続。届け先は合っている |
| 情報提供リプライが月1件以上ある | 継続。流入がゼロでも**データ収集の対価だけで運用コストに見合う** |
| どちらも満たさず、流入も月50未満 | 型を変えるか撤退。Threads との相性がなかったと判断する |

流入だけを基準にしない。**情報が集まること自体が、このサイト群にとっては流入と同等以上の価値がある**ため。

## 11. やらないこと

ADMIN.md の掲載ルールを SNS にも適用する。

- 他サイトの紹介文を投稿に転載する／語尾を変えて使う
- チラシ画像・写真・ロゴの無断掲載（**画像を使うなら自作のカード画像のみ**）
- 未確認情報（`pending`・`resident`）を確定情報として投稿する
- 自動フォロー・自動リプライ・相互フォロー企画（スパム判定リスク）
- 同じ文面の連投、短時間の連続投稿
- 情報元を書かない告知

「下書き生成のみ」を選んだことで、**Meta の自動化ポリシーに抵触する経路が最初から存在しない**という副次的な利点がある。API 連携を入れる時は、この点を再検討すること。
